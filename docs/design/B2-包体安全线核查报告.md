# 包体安全线核查报告（B2）

> 项目：微信小程序「旅行攻略生成器」 · 核查日期：2026-09-08 · 方法：静态实测（源码/图片逐文件累计）
> 关联：v1.9.0 数据扩展后（66 城 / 1007 坐标 / 461 experiences）的包体健康复核

## 一、结论（TL;DR）

**当前安全，余量充足。** 有效上包体积估算约 **0.94～1.09 MB**，距主包红线 **2048 KB（2 MB）** 还有 **约 900 KB～1100 KB 余量（≈45%～54%）**。v1.9.0 的城市/坐标扩充未构成包体压力，未来继续扩城、扩景点仍有充分空间，无需分包改造。

## 二、红线规则（微信官方，2026 现行）

| 约束 | 上限 | 本项目现状 |
|---|---|---|
| 主包（含 TabBar 页与公共资源） | **2048 KB（2 MB）** | ~1.0 MB ✅ |
| 单个分包（普通账号） | 2048 KB | 未使用分包 |
| 全部主包 + 分包总量（普通账号） | 20 MB（服务商 30 MB） | 远低于 |
| 启动即下载体积 | 主包越小越好 | TabBar 4 页全在主包 |

> 依据：微信官方《分包加载》文档。本项目 **未配置分包**，全部代码/资源进主包 → 以 **2048 KB 为主包安全线**。

## 五、占大头拆解 & 未来增长预算

1. **data.js（380 KB）是主包主导因子**，超过总上包 1/3。66 城单城平均 ≈ 5.8 KB（含 experiences/areas/foods 等完整 curation）。按此速率，**即便数据再翻一倍（~120 城 + 2000 坐标）也仍在红线内**。
2. 图片资源健康：全部 ≤ 8 KB、无大图。icons 66 张 264 KB 为自绘 UI 图标，替换成本高、压缩空间小，无需处理。
3. **潜在可清理**：5 张未引用图片（`images/tab-index/tab-more/tab-plan/tab-today.png` 旧版非高亮 tab 图 + `brand/logo-144.png`）合计 18 KB —— 不影响安全线，但可顺手删除。

## 六、建议动作（非阻塞，按需执行）

- [ ] **显式 packOptions.ignore**：在 project.config.json 声明 `tools/`、`.qr/`、`README.md` 排除，不再依赖「上传忽略未使用文件」的隐式兜底（更可预期、防未来误打包）。
- [ ] 删除 5 张未引用图（-18 KB，可选）。
- [ ] 设置体积警戒线：上包估算 > 1,600 KB 时做一次复查（届时触发条件大概率为 data.js 持续增长）。
- [ ] **若未来逼近红线**（预计很远），两条路径：① 数据瘦身（字段缩写/拆 foods 按需）；② 分包化 —— 但 TabBar 4 页共用 travel/data，**数据只能留主包**，故分包对主包体积帮助有限，届时以 ① 为主。

## 七、核查方法备注

- 图片引用集 = 遍历全部 wxml/wxss/json 中的 `images/*.png` 字面量；`images/icons/` 因页面存在 `{{}}` 动态拼接引用，按整目录计入（保守）。
- JS 压缩档按 ×0.8 估算（已开 minified）；data.js 为单行 JSON 字面量，压缩收益≈0，已按原样计。
- 精确上包数字以微信开发者工具「详情 → 代码包大小」或 `cli upload` 返回值为准（本报告为磁盘静态测算，误差 ±10% 内）。
