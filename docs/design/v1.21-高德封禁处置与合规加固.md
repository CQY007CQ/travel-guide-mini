> 日期：2026-09-14

## 一、事件原文要点

处置结果：

| 项 | 内容 |
|---|---|
| 违规 KEY | `b4f58a…` |
| 违规接口 | `v3/place/text`（关键字搜索） |
| 处置方式 | 封禁该 KEY 的该接口权限 |

## 二、封禁范围定位（实测）

对 `tools/geocode.keys` 中全部 KEY 逐把探针（`geocode/geo` + `place/around` + `place/text`）：

| KEY | geocode/geo | place/around | place/text |
|---|---|---|---|
| `61d076…16c2` | ✅ 10000 | — | ❌ 10044 配额超限 |
| `b0d7e1…ce12` | ✅ 10000 | — | ❌ 10044 配额超限 |
| `664f22…389f` | ✅ 10000 | — | ❌ 10044 配额超限 |
| `d6031c…4dc4` | ✅ 10000 | — | ❌ 10044 配额超限 |
| `fad9f7…06b9` | ✅ 10000 | ✅ 10000 | 🛑 **阿里「比西」风控 punish 页** |
| `6339c2…ba4c` | ✅ 10000 | ✅ 10000 | ✅ 10000 |
| `b4f58a…91af`（已封） | ✅ 10000 | ❌ 10044 | 🛑 已封禁 |

**结论：这是「接口级」处置，不是「账号级」封禁。**

- 被封 KEY 调 `geocode/geo` 仍返回 `10000 OK` → KEY 本身与账号都存活
- 全程未出现 `10026 INVALID_REQUEST`（「账号处于被封禁状态」）—— 这是唯一的账号级封禁码，
  一旦出现，**全部接口一起失效**，且只能靠控制台工单申诉
- `fad9f7` 返回的是 HTML（`bixi.alicdn.com/punish/…&action=deny`，带 `rgv587_flag:sm`），
  不是 JSON 错误码 —— 属**行为风控拦截**，且是接口级的：同 KEY 的 around / inputtips / regeo 全部正常，
  同一 IP 下 `6339c2` 的 place/text 也正常 → 判定为 KEY + 行为级，不是 IP 级

> 探活一行模板（JSON = 活的，HTML = 被风控）：
> ```bash
> curl -s "https://restapi.amap.com/v3/place/text?key=$K&keywords=晋祠&city=太原" | head -c 300
> ```

## 三、根因（为什么会被盯上）

本项目的既有工作流同时踩了协议四条红线：

| 条款 | 要求 | 本项目此前做法 |
|---|---|---|
| 4.12.3 | 禁止爬虫式访问、抓取、存储、缓存 | `place/text` 按关键词 + 城市批量刷，落盘成 `amap-spots-cache.json` / `SPOT_COORDS` |
| 3.5 | 禁止直接存储、缓存或以技术手段抓取本服务数据 | POI 数据全量落盘进 `utils/data.js` |
| 3.7 | 超限须付费；不得规避限流 | `drain-all-keys.sh` 的设计目标就是「每日主动用光所有 KEY 免费额度」 |
| 4.5 | 一个 KEY 只能用于一个应用 | 6~7 把 KEY 轮换共用于同一应用 |
| 3.1 | 个人认证仅限个人研究学习，不得用于生产 | 小程序已上线（v1.2.4 审核中） |

**所以「多 KEY 轮换绕过配额」+「批量抓取后落盘」这两件事，在服务端日志里是明摆着的违规证据。
本次只封一个接口，属于较轻处置 —— 继续跑会把「接口级」升级为「账号级」（10026），届时全接口失效。**

## 四、本次加固（代码改动）

### 4.1 新增 `tools/data/_amap-compliance.mjs`（合规护栏，所有高德请求的唯一出口）

- `assertAllowed(qs)` —— `v3/place/text` 一律**抛错**，从机制上保证请求不可能被发出（不是提示，是硬拦）
- `isPunishPage(body)` —— 识别阿里「比西」punish 页（`bixi.alicdn.com/punish` / `rgv587_flag` / `x5secdata`）
- `describePunish(body)` —— 提取 `action` / `uuid` 便于留证
- `BAN_HINT` —— 统一的风控熔断提示文案

### 4.2 逐个调用点处置

| 文件 | 原做法 | 现做法 |
|---|---|---|
| `fetch-amap-spots.mjs` | 通道 C `--mode text` 用 `place/text` | **函数体清空为抛错**，`--mode text` 直接 `exit 4`；`--check` 移除 place/text 探针 |
| `fetch-food-shops.mjs` | `place/text` + `types=050000` | 改 `place/around`（城市中心为锚、半径 50km、keywords 用 `|` 分隔） |
| `_resolve-poi-by-text.mjs` | `place/text` 解析缺口坐标 | 改 `assistant/inputtips`（独立「辅助服务」配额），成功判据由 `status` 改为 `tips` 数组 |
| `geocode-fix.mjs` | 高德通道 `place/text` | 改 `place/around`；缺城市中心则跳过该条 |
| `drain-all-keys.sh` / `finish-burn.sh` | — | 顶部加 4.12.3 封禁警告横幅 |

所有请求层同时加了 **punish 页识别 + 立即熔断整轮**（绝不重试），并把无效的 `fetch(…,{timeout})`
换成 `AbortSignal.timeout()`（`timeout` 选项在 Node 的 fetch 里本来就无效）。

### 4.3 批量抓取总闸（重要）

`fetch-amap-spots.mjs` 与 `fetch-food-shops.mjs` **默认拒绝执行**（`exit 5`），
必须显式 `AMAP_BULK_OK=1` 才放行。

理由：协议 3.5 禁止存储/缓存本服务数据 —— 只要是「批量抓取后落盘」，换哪个接口都还是同一违规类型，
这次只是恰好点到了 `place/text`。`--check` 体检不受总闸限制。

```bash
node tools/fetch-amap-spots.mjs --mode around --only 太原        # 🛑 exit 5，不发任何请求
AMAP_BULK_OK=1 node tools/fetch-amap-spots.mjs --check           # ✅ 体检仍可跑
```

### 4.4 落盘方式

改动经一次性原子脚本 `tools/_apply-amap-compliance.mjs` 完成：**每条替换先断言「恰好命中 1 次」，
全部通过才写盘，任一条不满足则整体放弃**（避免 `Edit` 静默回滚问题）。
原文件备份于 `tools/_bak-amap-compliance-<stamp>/`。

门禁：19 处替换全命中；5 个 `.mjs` 过 `node --check`；2 个 `.sh` 过 `bash -n`；
护栏单测（拦截 place/text、放行 around/inputtips/geocode、punish 识别命中且不误判 JSON）全绿。

## 八、不要做的事

- ❌ 不要用新 KEY 继续跑同样的批量抓取 —— 风控是按**行为**判定的，换 KEY 不解封，只会扩大处置范围
- ❌ 不要用亲属 / 他人实名信息代绑 KEY 申请 —— 这是明确的高频封禁点，且实名不一致会直接导致认证失败
- ❌ 不要对 punish 页做重试 —— 每次重试都在加重判定
- ❌ 不要试图改参数 / 换 IP / 模拟浏览器绕过风控（协议 4.12.3 后半句明确禁止「避开或试图避开」）
