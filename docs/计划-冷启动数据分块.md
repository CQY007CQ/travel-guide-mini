## 一、实测基线

## 二、体积构成（解压后）

| 数据块 | 原始 | 占比 | 首屏是否需要 |
|---|---|---|---|
| `CITIES.experiences`（26357 条玩法/体验） | 2.32 MB | **27.7%** | ❌ 仅生成行程时需要 |
| `SPOT_COORDS`（24358 点） | 924 KB | 10.8% | ❌ |
| `SPOT_TICKETS` | 757 KB | 8.8% | ❌ |
| `FOOD_SPOTS` | 657 KB | 7.6% | 部分（美食页） |
| `SPOT_INFO` | 203 KB | 2.4% | ❌ |
| `SPOT_DETAILS` | 144 KB | 1.7% | ❌ |
| 其余 | ~3.6 MB | | |

单城 `CITIES[i]` 平均约 3.8 KB，其中 `experiences` 占 **90%**（北京 180 条 = 18.1 KB / 20.1 KB）。

**结论：首页只需要「城市名 + 省份 + 简介」，却要先付出整包解压解析成本。** 其中 `experiences` 一项就占 27.7%，且对首屏完全无用。

## 四、为什么这次没落地

拆分数据块本身不难，难在**同步契约**：

- `planner.js` 的 `buildPlan()` / `buildMultiPlan()` / `buildProvPlan()` 全是**同步函数**，内部直接读 `CITIES[i].experiences` 选景点；
- 一旦 `experiences` 放到「不 await 的懒加载块」，首页能秒开，但用户点「生成行程」时数据可能还没到 → 生成空行程或直接抛错；
- 要让 `buildPlan` 变成异步，会牵动所有调用点（首页 3 处、全省游、多站、`_test-*` 全套回归），
  而本项目历史上最严重的事故就是**首页白屏 / 「无法加载完整数据内容」**（v1.19.97–99 三连修），
  根因正是数据块加载时序；微信「分包异步化」还要求 `require.async` 实参必须是**静态字面量**。

**判断：这是「必须上真机验证」的改动，没有设备就在生产包上动它不划算。** 记录方案，等有验证窗口再做。

## 五、落地步骤（验证窗口内执行）

1. **改 `tools/pack-data.mjs` 分块策略**：把 `CITIES[].experiences` 抽到独立块（预计 500 KB 压缩后），
   主块降到约 1.3 MB；同步更新 `utils/data.js` 里的静态 `require.async` 字面量清单（脚本内已有断言防退化成变量）。
2. **`utils/data.js` 新增 `initHeavy()`**：只在需要时下载 experiences 块；`initData()` 保持现有语义不变（不阻塞）。
3. **加 `T.readyFull()`**：`await ready()` + `await initHeavy()`。
4. **生成入口前置等待**：`pages/index/index.js` 的 `generate()` 改 async，首行 `await T.readyFull()`；
   多站 / 全省游分支同样处理。其余读 experiences 的入口（深度玩法等）同样加等待。
5. **回归**：`allcheck.sh` 全绿 + 真机冷启动录屏对比首屏时间 + 微信 IDE「清缓存重编译」验证非残包。

预期收益：首屏阻塞下载量 2031 KB → 约 1.5 MB（**-25%**），解析时间同比例下降。

## 六、替代方案（如果不想动时序）

在**不拆块**的前提下，唯一有效手段是**减小数据本身**：

- `experiences` 每城保留前 12 条（当前平均 35 条）→ 约省 60% 体积，代价是「深度玩法」页内容变薄；
- `SPOT_TICKETS` 保留 4A/5A 级景点门票，其余并入参考价 → 约省 400 KB。

这是**内容取舍**，需要产品侧拍板，不适合由工程单方面决定。
