## 二、缺陷清单

### P0-1　AI 金额禁令过宽，与上下文真实数据冲突（已修复）

**现象**：`aiContextOf()` 会向模型注入两行含金额的真实事实：

```
预算：已花 ¥0 / 预算约 ¥5001 · 还剩 ¥5001。
本机已记录花费：今日 ¥0 / 累计 ¥0。
```

而上一轮刚把提示词改成「**绝不输出任何金额**」。两者叠加后，用户问「我预算还剩多少」「今天花了多少」时，模型会把**有确切数据的问题**答成「以 App 内对应页为准」。
这同时违反两条项目原则：能力宣称属实、有数据就用。

**根因**：把「禁止编造外部报价」错误地扩大成「禁止一切金额表达」，没有区分
「上下文/用户已给出的金额（事实）」与「需要外部查询的票价房价（易编造）」。

**修复**：禁令收窄为「不编造或估算票价/房价/机票等外部报价」，并新增一条正向义务
「上下文或用户已明确给出的金额必须如实复述，但不得据此反推单价」。三处落地同步：

- `utils/ai-agent.js` `AI_MASTER`（主包）
- `subpkg/assistant/ai-prompts.js` `MASTER`（分包）
- `tools/cloud/llmProxy/index.js` `GUARDRAIL`（云函数，**需本人重新部署才生效**）
- `tools/prompt/engine.mjs`（管线真源）

**验收口径**：`run10.mjs --offline` 契约里新增两条并列断言 ——「禁编造报价」与「允许复述真实金额」
必须**同时**成立（只禁不复述会让真实问题被拒答）。当前 18/18、18/18、11/11 全绿。

**复现**：

```bash
node -e 'const T=require("./utils/travel.js");T.ready().then(()=>console.log(T.budgetGauge({budget:"mid",customAmt:5000,people:3,days:3})))'
# → 已花 ¥0 / 预算约 ¥5001 · 还剩 ¥5001   ← 这行会进模型上下文
```

### P1-1　浅色主题辅助文字对比度不足

| 主题 | 变量 | 色值 | 最低对比度 | 判定 |
| --- | --- | --- | --- | --- |
| 浅色 | `--t4` | `#7d92ab` | **2.77** | 不合格 |
| 浅色 | `--acc` | `#b3872e` | **2.83** | 不合格（若作文字） |
| 浅色 | `--gold` | `#d4a94e` | **1.90** | 仅可作底色，不可作文字 |
| 暗色 | `--t4` | `#5b6b82` | **2.93**（对 panel `#222222`） | 不合格 |
| 暗色 | 其余语义色 | — | 5.00–13.78 | 合格 |

**影响面**：`--t4` 用于攻略页 `.gi-x` / `.gq-a`（22–23rpx）、美食页 `.dish-hint`（21rpx）、
地图页 `.approx` / `.dim`、记账页 `.lg-date`（21rpx）、百宝箱页脚。全是小字号辅助文字，
低对比度下在户外强光几乎不可读 —— 而这是旅行场景的主战场。

**整改**（各改一个变量值，不动模板）：

- 浅色 `--t4: #7d92ab` → `#5b6b82`（4.70 ✓，与 `--t2` 同值，语义上「辅助文字」本就该一致）
- 暗色 `--t4: #5b6b82` → `#8fa3bc`（6.16 ✓，与暗色 `--dim` 统一）
- `--acc` 浅色 `#b3872e` → `#8f6a1f`（4.28 △，可接受）；若追求达标用 `#7a5a19`

**验收口径**：建议新增对比度门禁（见第五节 A-1），把「文字色 × 四种表面色」全部算一遍，
任一项 < 4.5 判红，防止后续调色回潮。

### P1-2　金色底 + 白字 = 2.19:1

```css
/* subpkg/spotsearch/spotsearch.wxss:22,41,52,88,92 —— 选中态 chip / 主按钮 */
background: var(--gold);  color: var(--on-gold);   /* --on-gold: #ffffff */
```

`#ffffff` on `#d4a94e` = **2.19:1**。而项目里**同时存在** `--chip-tx: #14100a` 就是为金底准备的深色文字
（`#14100a` on `#d4a94e` = 7.6:1）。两套金底文字色并存，其中一套不可读。

**整改**：`--on-gold` 浅色改 `#14100a`（与 `--chip-tx` 合并为一个变量）；
若设计上必须白字，则把金底压深到 `#8a6a1f` 以上（白字需 ≥4.5）。

**验收口径**：同上对比度门禁，额外断言「同一 `background: var(--gold)` 的规则里，
`color` 不得为 `--on-gold` 白值」。

### P2-1　100% 行程把「片区｜多品牌」当成一家酒店名

实测 847/847 个城市生成的行程，首日第一条都是这种形态：

```
抵达 + 入住「市中心/高铁站附近｜全季·亚朵·维也纳·丽枫」
抵达 + 入住「束河古镇·古城边｜丽江古城客栈（大水车旁）·束河悦榕庄度假村」
```

数据源 `city.hotels` 本是 `{tier, place, brands}` 三元结构，`planner.js:455` 拼成
`` `${place}｜${brands}` `` 后又套进 `入住「…」`，语义上被读成「一家酒店的完整名字」。

**影响**：用户会去找一家叫「市中心/高铁站附近｜全季·亚朵…」的酒店；带爸妈的行程尤其容易误解。
命中率 100% 的行程，属于高频可见缺陷。

**整改建议**（只改文案，不动数据）：`hotelPick` 拆成两段 ——
`抵达 + 入住「市中心/高铁站附近」`，note 追加「片区可选：全季 / 亚朵 / 维也纳 / 丽枫」。
需同步改 `planner.js:455` 与 `1416` 两个构造函数、6 处调用点的 note。

**为什么我没有直接改**：`入住「…」` 文案被多处测试断言引用，属核心生成逻辑。
按测控流程，这类改动应先补断言、再改文案、再跑全链，不宜在报告阶段顺手改掉。

### P2-2　同一条问题，联网与离线口径不一致

- 联网（LLM 通道）：被禁报价
- 离线兜底（`subpkg/assistant/ai-brain.js:621`）：直接输出 `门票：¥XX`

我们自己收录的真实数据带出处标注，展示本身不违规；但**同一入口两种结果**会让用户认为 AI 不可靠。
**整改建议**：二选一并写进文案 —— 要么两条通道都展示「App 收录的真实票价 + 采集时间」，
要么都用「以景区公告为准」，把差异收在数据层而不是提示词层。

### P2-3　城市名带后缀不归一

`canonCityName()` 只去「市」后缀，实测：

| 输入 | canonCityName | findCity |
| --- | --- | --- |
| 丽江市 | 丽江 ✓ | 丽江 ✓ |
| 北京市 | 北京 ✓ | 北京 ✓ |
| **丽江古城** | **丽江古城** ✗ | 丽江古城（未命中真实数据） |
| **丽江地区** | **丽江地区** ✗ | 丽江地区（未命中） |

深链 `_applyDeepLink()` 有白名单校验（`if (pIdx < 0) return`），所以外部链接**进不来**，
风险被限制在内部路径（收藏 / 历史 / 草稿）。
**整改建议**：`canonCityName` 增加剥「古城 / 地区 / 自治州 / 新区 / 景区」后缀的重试，
命中则归一、不命中保持原样 —— 纯增量逻辑，不改变现有命中行为。

### P2-4　部分测试在无 `wx` 环境下静默走默认值

全链回归日志里有 8+ 处：

```
[diag][store] store · ReferenceError: wx is not defined
```

`store.get()` 的 catch 会吞掉异常并返回默认值，于是这些测试实际测的是「空存储」分支，
**看起来通过、实际没覆盖真实存储行为**。这不是产品缺陷，但会削弱门禁可信度。
**整改建议**：纳入门禁（见第五节 A-3），出现该日志即判红。

## 三、经实测**应当关闭**的伪问题（避免无效改动）

测控的职责里有一半是**阻止不必要的改动**。以下两条曾被列为待办/疑似故障，实测不成立：

**① 「美食页 setData 全量店铺无分页」不是问题。**
421 个城市、9625 家店，按页面真实映射后的载荷：

| 城市 | 店铺数 | setData 载荷 |
| --- | --- | --- |
| 成都 | 54 家 | **13.8 KB** |
| 北京 | 52 家 | 13.5 KB |
| 重庆 | 51 家 | 12.9 KB |
| 平均 | — | 4.6 KB |

微信单次 `setData` 建议 < 256KB，实测最大 13.8KB，有 **18 倍余量**。
分页改造会引入「切页丢筛选态」「滚动位置跳变」等新缺陷，**收益为负**，建议正式关闭该待办。

**② 线上分享链接「资源全部 403」不是故障。**
`curl` 直接取 `lib/runtime.js` / `app.js` / `shell.css` 全返回 403，响应体是平台自己的
「链接不完整」页（`<title>链接不完整</title>`）。带首页会话 cookie（`__wb_rsc`）复取后：

```
首页           HTTP 200   2.33s   10.6 KB
lib/runtime.js HTTP 200
app.js         HTTP 200
shell.css      HTTP 200
```

**平台鉴权行为，不是构建产物损坏。** 若据此报 P0 并「修复」，会浪费一整天且改坏东西。

同一批代码，我先后读出过 **6 个假结论**，全部是**测试写错**而不是产品有问题。列出来是为了让读报告的人知道该信哪部分：

## 五、改进方案

### A. 近期（本轮可落地）：补 3 条自动化门禁

当前 61 步门禁覆盖极广（2875 条断言），但**全部是「结构/契约」断言**，缺三类「数值/有效性」断言：

**A-1　对比度门禁**（新增 `tools/check/check-contrast.mjs`）
解析 `app.wxss` 两套主题的语义变量，对「文字色 × {bg, card, well, panel}」逐一算 WCAG 对比度，
任一 < 4.5 判红并打印 `变量 / 色值 / 对比度 / 最低组合`。本次 P1-1、P1-2 就是它该拦下的。

**A-2　金额口径一致性门禁**
断言 `cloud.aiContextOf` 注入的金额字段（`预算/已花/累计`）与提示词的「允许如实复述」条款
**同时存在**。防的是「改了这边忘了那边」—— 本轮 P0 正是这样产生的：
提示词单方面加严，上下文照常注入，两边打架。

**A-3　测试有效性门禁**
扫描回归日志，出现 `ReferenceError: wx is not defined` 即判红，强迫测试补 `wx` 垫片。
否则「通过」可能是空数据上的通过。

> 注意：新增门禁会改变 `allcheck.sh` 的步数（当前 61），而 `check-doc-consistency` 会校验材料里的
> 步数口径。落地时须同步 7 份交付材料，属一次版本号级别的动作，建议与下次发版合并。

### B. 中期：把「Node 侧代理真机」的缺口补上

现状：**所有自动化断言都跑在 Node 沙盒里**，E2E 脚本存在但不在回归链内。
以下 4 类只能在真机/模拟器上暴露，属当前最大盲区：

1. 分包 `require.async` 的真实时序（本轮 P0 级隐患都在这块）
2. 地图 marker 数量 > 30 时的手势性能与 pin 重叠
3. canvas 分享图导出的真机渲染差异
4. iOS 日期解析差异（代码已规避 `new Date("YYYY-MM-DD HH:mm")`，但未真机验证）

建议：把 `tools/dev/e2e-smoke.cjs` 纳入发版前手工清单（不进 `allcheck`，避免步数口径变动），
每次发版跑一次并留档截图。

### C. 长期：缺陷分级与影响面声明

1. **P0 阻断发布**：涉及合规红线（伪行程/伪造数据）、AI 拒答真实数据、支付/分享失败。
2. **每次改动附「影响面声明」**：改了提示词就说明「哪些数据会进上下文」；改了变量就说明
   「哪些页面在用这个变量」。本轮 P0 与 P1 都是「单点改动、跨模块生效」造成的。
3. **伪问题登记册**：像第三节那样把「实测不成立」的待办正式关闭并留档，
   防止半年后又被当成待办翻出来改一遍。

## 八、整改记录（本轮已完成，`allcheck` 61/61 · 2890 条断言 · RC=0）

### 8.1 对比度：从 9 处不合格 → 0 处

门禁上线后一次扫描把问题从「报告的 2 处」扩展到「9 处」，逐条修正：

| 场景 | 整改前 | 整改后 |
| --- | --- | --- |
| 浅色辅助文字 `--t4` | 2.77:1 | **4.70:1** |
| 暗色辅助文字 `--t4` | 2.93:1 | **6.16:1** |
| 金底文字 `--on-gold` | 2.19:1 | **8.65:1** |
| 暗色红底文字（新增 `--on-red`） | 3.18:1 | **5.96:1** |
| 浅色金色文字（攻略/我的/百宝箱/行程保存态） | **1.90:1** | **4.57:1** |
| 浅色排名徽章 `.ins-rank` | 3.15:1 | **8.65:1** |
| 浅色预算徽章 `.bc-no` | 3.83:1 | **8.65:1** |
| 暗色日期快捷选中 `.dp-chip.on` | **1.00:1（文字与底色同色，完全消失）** | **8.65:1** |
| 浅色强调色 `--acc` | 2.83:1 | **4.57:1** |

同时修掉两处「同一变量被当成两种语义」的误用：
- `--on-gold` 既被当「金底上的文字」（该用深色）又被当「金色文字」（该用亮色）→ 后者改用 `--gold-tx`
- `.rb-score` 白字压渐变，不能跟着 `--on-gold` 变深 → 显式写 `#fff`

### 8.2 新增门禁 `tools/check/check-qa-rails.mjs`（4 组，串进现有 step，61 步口径不变）

| 组 | 内容 | 上线即抓到 |
| --- | --- | --- |
| A 对比度 | 同规则「文字色 × 背景色」+ 语义变量 × 四种表面色，均需 ≥ 4.5:1 | 7 处规则级 + 8 个变量级不合格 |
| B 金额口径一致性 | 断言「禁编造报价」与「允许如实复述真实金额」**同时**存在，且不得回退成一刀切「绝不输出任何金额」 | 防住本轮 P0 复发 |

## 九、代码整理期追加发现（同日）

整理 `tools/` 目录时顺带核查「谁在引用谁」，抓到一类**比 bug 更难发现的问题：覆盖被删了但没人知道**。

### P1-A 拖拽排序回归测试在批量轻量化中被删除，实际零覆盖

- **事实链**：`_test-plan-handlers.mjs` 第 3 行注释写着「拖拽已另有 `_test-v11977-drag.mjs` 覆盖」，
  但该文件**不存在**。`git log --all` 查到它由 `1f685ef` 引入（185 行 / 8 组场景），
  在 `1b00c16`「资源管理器轻量化 —— 文件 736 → 302」里被 `D`（删除）。
- **为什么被删**：该测试靠 `indexOf(" onDragStart") ~ indexOf(" onMove")` 从**单文件** `plan.js`
  截取方法体。T4 拆分把三个 drag handler 搬到 `pages/plan/p-edit.js`，而 `onMove` 恰好排在
  `onDragStart` **前面** → 截取区间反了 → 直接 `✗ 抽不到 handler 源码` 退出。
  清理时看到「跑不过」，就按坏文件删掉了 —— 而它覆盖的正是**本环境唯一测不到**的手势交互。
- **危害**：拖拽是行程页最易回归的交互（位移算法、时段坑位、框架行保护、落位时数据被清空）。
  零覆盖期间任何改动都不会报警，且注释仍在告诉后来者「已覆盖」。
- **修法**：改用 `pageSrc()`（页面 + 同目录 `p-*` 模块拼成一份源码）+ **逐方法抽取**
  （不再用「两个方法名之间」的区间截取，方法顺序一变就失效），恢复后 30 断言全过并重新入链。
- **同类风险**：凡「读页面单文件做正则断言 / 抽取」的测试与门禁，T4 拆分后都会静默失效或假绿。
  这是本项目第二次踩（第一次是门禁正则假绿，已统一走 `pageSrc()`），已写入 `tools/README.md` 硬规则。

### P2-A 用户可感知的失败路径被空 catch 吞掉（2 处）

| 位置 | 原行为 | 现行为 |
| --- | --- | --- |
| `pages/more/more.js` 深度玩法入口 | `A.initDeep().then(...).catch(function(){})` | 分包下载失败时 `EL.note("more", err, ...)` 留痕，入口保持隐藏（不假装可用） |
| `pages/plan/p-edit.js` 拖拽启动 | 量尺条数不符 → 直接 `return`，**无声无息** | 不启动（防错位）**+ 提示「拖动暂不可用，点行展开用 ↑↓ 调序」+ 诊断日志**，3 秒节流防刷屏 |

`p-edit.js` 这处的性质是「防错位」的正确保护措施配了「零反馈」的交互 —— 用户只会判定「按住拖没反应」，
而同一功能的 `↑↓` 替代路径就在同一行展开区里，提示一句即可自愈。
